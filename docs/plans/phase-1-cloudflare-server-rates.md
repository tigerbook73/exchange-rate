## 1. 已确认目标

用户已授权改变原有“设备端历史为唯一存储、无后台采集、双平台部署”的边界：

- 全部部署到 Cloudflare，不再以 Vercel 部署兼容性作为验收目标。
- 服务端主动获取并持久保存业务数据，客户端主要查询服务端已有数据。
- 浏览器打开、刷新、返回前台、缓存失效或首次访问均不得触发源站抓取。
- 服务端每分钟采集，固定保存整 5 分钟点；两个固定点之间只保留一个随采集更新的临时点。在独立分支测试。

本轮“日数据”已明确为分时走势，同时保留每日单值历史折线，不扩展为日 K 线。请求按实际发起时间截断到分钟归属：例如 10:05:05 发起就算 10:05，即使跨分钟返回也不改归属。固定点失败时可使用前 5 分钟内最近的真实成功采集值，保留实际来源与回退标记；详见 3.1.1。

界面只查看当日分时，不提供今天 / 昨天 / 前天的手动选择。三日保留仅作预备：当源站 `publishedAt` 的北京时间日期仍早于今天时，显示最近有效报价日的数据，并在卡片和分时图明确标出完整日期，不能把今天采到的旧报价当作今天的新报价。同日报价未变仍有效，不依据固定开盘时间或工作日猜测失效。

分时显示补充：裁掉首尾无有效数据时段，标题为“日期 开始时间–结束时间”；内部空档沿用前一个有效采集值（来源不递推），仅用于图表展示。开头增加前一有效日末值短水平参考线，明确来源日期；没有当日采样不独立生成走势。显示层处理不改变 D1 / IndexedDB 真实缺失状态、5 分钟回退规则及采集成功计数。

图表入口统一为时间范围：默认“30 天”展示每日历史；“1 日”展示上述分时走势，“7 天、90 天、半年、一年”也展示每日历史；不再设置“日内走势 / 每日历史”两级切换。

时间范围选项保持单行，超出宽度时横向滑动并提供左右移动按钮，到达边缘时隐藏对应按钮，不让页面整体横向溢出。

## 2. 目标架构

```text
Cloudflare Cron（每分钟）
  → 独立采集 Worker → 工商银行 JSON API → 校验 → D1 业务数据
                                                   ↑
浏览器 / PWA → OpenNext 网站 Worker → 只读查询 API ──┘
    └─ IndexedDB / Service Worker：设备离线缓存

OpenNext → 独立 R2 增量缓存（继续仅存框架缓存）
```

- 独立采集 Worker 直接复用 `src/lib/` 的解析和日期逻辑，不经 Next.js HTTP API 执行采集，避免为定时任务引入页面处理开销。
- D1 是业务数据的权威存储；R2 继续专供 OpenNext 增量缓存，不混存业务历史。不引入 KV、Queues 或 Durable Objects，除非后续证据表明必需。
- 网站 API 只有数据库读取权限的应用职责。D1 binding 本身不等于数据库级只读授权，须通过模块边界与测试保证没有写入或抓取路径。
- 源站抓取只允许来自采集任务和显式运维初始化命令；不提供用户可调用的 `force`、`refresh-source` 或抓取管理端点。
- 开发、测试、生产使用独立数据库；测试网站与采集 Worker 不绑定生产业务库或生产缓存桶。
- Git 分支本身不隔离云端资源。每次部署前核对目标账号、Worker 名称、D1 ID、R2 桶、网站的 OpenNext 自引用 service binding 和 Cron 配置；测试网站的自引用必须指向测试网站自身。使用明确的测试配置与命令，不以默认 `pnpm deploy` 代替测试部署。
- 首次推送测试分支前，核实并关闭 Vercel 对该仓库的生产及分支预览自动部署，避免测试分支仍触发 Vercel 构建。该操作不等于删除现有部署；分支推送仍需用户明确授权。

## 3. 采集与数据质量

### 3.1 采集粒度与存储

- 现价改用工商银行 `getLatest` JSON API 的 AUD `foreignSell`（人民币 / 100 澳元），转换为项目每澳元口径；使用完整日期和秒级时间。旧网页源和跨年推断代码保留但不启用，不自动回退。
- 每个预定 1 分钟槽位记录一次任务结果；报价相同也算成功检查，但不保留每分钟历史价格序列。
- 区分 `scheduledAt`（预定调度时间）、`requestedAt`（源站请求实际发起时间）、`receivedAt`（响应读取完成时间）、`publishedAt`（源站报价发布时间）。业务采集分钟为 `floor(requestedAt 到分钟)`；返回时间与 Cron 计划时间只用于延迟诊断，不用于替换业务归属。
- 任务发起前核对窗口和已提交分钟，维持源站请求 8 秒超时，采集执行预算短于一分钟。调度迟到进入下一分钟时，记录原槽位迟到；若实际当前分钟尚无采集，可按实际发起分钟采集，不能倒填原计划分钟。当前分钟已有执行或有效尝试时跳过重复任务，避免积压调度恢复后密集重抓。
- 分别保存观察日期与报价日期：午夜后源站仍返回前一天报价时，记录“此时观察到旧报价”，不能把它写成新一天真实报价，也不能计入新一天 OHLC；UI 可显示旧报价但必须标明来源日期。
- 同一槽位重入幂等，采用数据库唯一键与原子写入；重复执行、并发和乱序写入不得让 latest 状态回退。不能依赖 Worker 实例内的锁。
- 新发起请求的结果不得被更早请求的迟到响应覆盖，成功采集状态按实际请求顺序单调更新；源站报价发布时间异常倒退须标记并避免覆盖更可信的 latest 报价。同一分钟重复提交由采集分钟条件与 revision 去重，允许偶发重复抓取，不以响应返回顺序决定胜负。成功检查时间独立更新：读到旧报价不代表采集失败，也不代表报价刚发布。
- 固定点 / 临时点、最近真实成功值、同步版本和变更标记通过 D1 事务批次原子提交；写库失败不能留下“任务成功但报价未保存”。取消租约锁；批次以随机 write_id 标识获准提交，条件 revision 防旧结果覆盖，失败批次不得写实体或变更标记。正常轮次仅一次读取与一次 batch，冲突允许跳过。实施阶段先完成这些 SQL 与冲突测试，再接真实 Cron。
- 金额优先以固定精度整数保存，API 输出保持当前价格单位；换算和有效范围根据现有解析器及 fixture 核对。
- 校验日期、价格、目标币种与结构；解析失败、超时、HTTP 错误不更新 latest 成功报价。异常信息不保存整份 HTML 或凭据。
- 补齐现有解析器的验证边界：空字符串不能经 `Number("")` 当作 0，价格必须为正且精度可接受；日期须验证真实日历合法性和合理未来偏差。历史结构缺失、空结果或行级解析异常不能静默当作完整成功并推进同步游标；错误须可诊断，暂不设武断的固定价格区间。

拟定逻辑表（实施前细化迁移 SQL 和索引）：

| 表                 | 职责                                                                                 |
| ------------------ | ------------------------------------------------------------------------------------ |
| `intraday_points`  | 整 5 分钟固定点，含真实 / 回退 / 缺失状态及真实采集来源；按点所属北京时间日期查询    |
| `daily_rates`      | 每日历史单值，区分源站历史与当天采样暂定值，不伪造 OHLC                              |
| `collection_state` | 单个临时点、最近真实成功值、分任务游标、最近尝试、连续失败数、采集策略及批次写入标记 |
| `collection_runs`  | 保留旧诊断供过期清理；新任务使用结构化日志，不逐轮入库                               |
| `sync_changes`     | 仅存变更版本、实体键和删除标记；不存历史分钟报价 payload，与业务变更原子提交         |

### 3.1.1 固定 5 分钟点与唯一临时点

- 固定点按北京时间 `:00、:05、:10……` 保存，点的日期和横轴使用这个固定分钟。10:00 与 10:05 是两个独立固定点；虽然从 10:00 数到 10:05 共有六次分钟采集，但 10:00 不会在下个周期重复保存。
- 10:01 至 10:04 每分钟采集一次，只覆盖同一个逻辑键 `live:<currency>`：10:02 成功后只保留 10:02 的临时点，不再保留 10:01 分钟点。临时点横轴为实际发起请求所属分钟，不预先画到未来 10:05。
- 10:05 所属分钟的请求成功后，将该值保存为固定点 10:05，并移除 / 隐藏同时间的临时点；10:06 成功后再产生唯一临时点。固定点不取 10:04 作为正常结果，也不要求精确在 10:05:00 发起。
- 例如 10:05:05 发起算 10:05；10:05:59 发起、10:06:03 返回也算 10:05。超过请求超时或无法通过提交 revision / 分钟条件的响应不得写入；归属规则不能放宽原有超时预算。
- 固定分钟 T 的采集失败或未触发时，从 `[T - 5 分钟, T]` 范围内取最近一次真实成功采集，按截断后的发起分钟判断范围，并记录 `sourceRequestedAt`、`sourceMinute`、`isFallback`。例如 10:00 失败，09:59 成功则固定点 10:00 使用 09:59；实际来源 09:55 也可用，09:54 不可用。
- 回退必须引用真实成功采集。若 10:00 是沿用 09:59，10:05 再失败，不能把 10:00 的沿用值当作真实采样继续沿用；实际来源 09:59 已超 5 分钟，此时 10:05 存储为缺失；分时显示层可按后述规则沿用，不伪装采集成功。未来 10:06 新获取的值也不能补成 10:05 的采集值。
- 若固定分钟 Cron 根本未触发，在后续任务覆盖最近真实成功状态之前，先用旧状态检查可补记的固定点。只使用该固定分钟以前已存在的真实采样；长中断不逐点抓取补历史，也不把恢复后的值倒填。仍在保留范围内且无法回退的固定点明确缺失。
- 固定点处理完成后，不论直接采集、回退或缺失，都清空所属分钟不晚于该固定点的临时点。例如 10:05 回退到 10:04 时，图上保留带来源标记的固定点 10:05，不再同时画临时点 10:04；最近真实成功值仍独立保存在状态中供后续判断。
- 普通分钟采集失败时不产生新的真实临时点；若之前成功的临时点仍在最新固定点之后，保留并显示该次更新失败。已经到固定点之前、超过回退窗口或属于旧日期的值不能当作当前周期有效临时点连线。最新报价卡片仍可显示最后已知报价，必须展示其来源时间与延迟状态。
- 报价发布时间和采集时间分别保留。跨日采到源站前一天报价，或 00:00 固定点回退到前一天 23:59 时，允许显示但必须标为旧报价 / 回退；不能当作新一天真实银行报价或用于伪造每日历史。

保留策略（2026-11-22 调整）：

| 数据         | 服务端保留范围                                   | 到期处理                                          |
| ------------ | ------------------------------------------------ | ------------------------------------------------- |
| 分钟临时点   | 每币种最多一个，另独立保存最近真实成功值用于回退 | 每分钟成功后覆盖，不保留整个最近 5 分钟的分钟序列 |
| 5 分钟固定点 | 北京时间今天及前两个自然日，共 3 天              | 删除早于前天 00:00 的固定点，不按滚动 72 小时计算 |
| 每日历史单值 | 长期保留，暂不设自动过期天数                     | 不随采样明细删除；初始回溯 365 天，随后持续积累   |
| 任务诊断记录 | 30 天                                            | 定时分批清理                                      |
| 同步变更记录 | 最近 3 天，公开声明最早有效同步游标              | 过期后不能继续使用旧游标；客户端重建有限窗口      |

- 全天运行时，3 个自然日最多约 864 个 5 分钟固定点，外加一个临时点，不把点数直接当作计费写入数。每日历史默认仍展示最近一年，展示范围不等于服务端存储期限。
- 临时点在写入时覆盖，不建立随后再清理的完整分钟价格表；同步日志与任务日志也不得暗中保存全部分钟价格。三日固定点、30 日诊断及变更标记按各自过期边界定时分批清理。先保障本轮采集写入，清理失败不回滚成功采集，记录进度供后续任务继续。查询 API 按逻辑保留范围过滤，不因物理清理延迟返回过期固定点。索引和删除也计入用量。
- 删除采样前保证对应日期的每日暂定值已独立保存；历史校准未完成时保留暂定状态及待修复日期，不为等待校准而无限延长采样明细保留。latest 报价独立存储，不因引用的明细过期而丢失。
- 不删除 `daily_rates`，也不删除完成缺测统计所需的采集起点和策略生效元数据。本期不提供日 K 线，不从仅保留的固定点声称能还原所有分钟波动。

### 3.2 允许的错漏

- 这是每分钟采集、只长期保留固定 5 分钟点和一个临时点的服务，不承诺逐笔完整记录或精确触发时刻。分钟内变化可能不可见，被临时点覆盖的中间波动无法事后恢复；数据源自身可能滞后。
- 允许偶发源站失败、调度延迟及漏采。正常失败等待下一轮，不循环密集重试，不在客户端补触发。
- 源站只提供当前快照时，遗漏的日内报价通常无法补回；日历史接口不能用于伪造日内数据。
- 有效采样可以因源站未更新而连续相同。固定点区分直接采集、前 5 分钟内回退与缺失；回退点明确标来源分钟，超窗存储为缺失；分时显示层仅在已有时段内部沿用前一有效采集值，明确来源。不能把失败或沿用值标成该分钟直接采集成功。
- 通过平台指标及结构化日志观察成功率、任务延迟和未执行槽位。只有超过当前时间容差的计划执行槽位才计入漏采；计划停采与失败分开。
- 覆盖率分母从本环境实际启用采集的时间开始，结合带生效时间的策略版本计算，不把建库前、未来、已超保留期或计划停采槽位算作失败。Cron 没有执行时不会写失败行，查询侧须根据预期槽位推导缺测，新版不逐轮写 `collection_runs`，不能再依赖该表推导当前采集成功率。
- UI 显示报价发布时间及离线 / 同步错误提示，不再显示服务端检查时间、本地演示或采集延迟提示。服务端状态仍保留用于同步与诊断。

### 3.3 采集时间窗口

- 首期建议全天、每周 7 天，每分钟采集一次；每日 1,440 次，每 30 天 43,200 次，另加历史同步与运维任务。源站请求量是原 5 分钟方案的 5 倍，不能用存储归并后的点数估算抓取次数。
- 先观察至少 14 天（包含两个周末）的发布与变动分布，再评估可配置停采窗口。有限样本只能支持策略选择，不能证明某时段永远不更新。
- 两周观察是缩短采集窗口的前提，不是全天采集版本完成基础验收或上线的硬等待期。观察期间保持全天策略，不自动缩窗。
- 不直接套用股票交易日历、外汇交易市场时间或柜台营业时间；也不因为连续若干次不变就自动认定休市。
- 如果以后选择受限窗口，应留边界缓冲，明确窗口外变化可能遗漏；若窗口外保留低频探测，就不能宣称该时段完全不抓取。
- Cron 表达式按 UTC；业务窗口在 `Asia/Shanghai` 判断，不受澳大利亚夏令时影响。受限窗口开启后，槽位之外在发出源站请求前跳过。

### 3.4 每日历史

- 测试库初始化通过显式运维命令回溯 365 天；命令可重复执行，失败可恢复，不依赖用户访问，不在 build 阶段抓取并写业务库。
- 历史任务有独立游标，不能取分时固定点、当天暂定值或沿用记录中的最大日期作为起点，否则今天已有样本会跳过昨天校准。游标记录最近成功历史响应范围和最后确认历史日期，另外保存未校准暂定日期与失败范围。
- 部署前校准从“最后确认历史日期本身、待修复范围起点”中较早者开始，过滤北京时间今天及未来记录。历史响应不含某日不能自动视为抓取失败，也不能把该日期标为真实报价。缺日沿用只表示引用已有报价，不能据此认定源站该日无记录或任务已成功覆盖。
- 每次通过统一部署入口发布之前，由本机 / CI 的 Node.js 同步历史并检查就绪，失败停止发布；日常分钟 Cron 不再校准历史。长期不部署期间，漏采 / 历史修正要等下一次部署或显式回填；未确认值继续标为暂定，失败不推进游标。历史回填不持有租约，在源站读取结束后合并最新分钟状态，再以条件批次提交；提交冲突由部署脚本有限重试。
- 当天值只信真实采集的源站报价，过滤 history 当天值；每日暂定值独立更新，不能被临时点覆盖而丢失。跨日后历史值校准前一日暂定值，不把回退点当作新的真实报价。
- 服务端每天首次成功提交采集状态时，从已存最近真实 / 暂定日报价补齐缺日至北京时间昨天，不等待新日期报价，源站失败时也补；不补今天、不向前倒填。补缺日期标记与实体共用原子批次，冲突后下轮重试；状态 SELECT 按需返回最近真实日记录，不增加分钟任务的 D1 往返。
- 显式修复命令及部署前历史校准修复已有内部 / 尾部空档；每个沿用值指向此前最近真实日期，不链式沿用、不覆盖已有真实 / 暂定报价。真实历史覆盖沿用值后，重新校准后续沿用值；补缺不推进历史确认游标、不写成真实日内采样。
- 历史任务与分钟快照任务分开设置运行状态、故障与预算；停采时间窗仅约束当日快照，历史任务只在部署前或显式回填时执行。

## 4. 客户端与查询 API

- 初期尽量保留 `/api/today`、`/api/history` 路径以简化 PWA 过渡；补充服务端版本、数据来源和新鲜度字段。
- 实施前冻结 API 契约：历史返回范围、真实 / 沿用 / 暂定来源、`carriedFromDate`、快照生成时间、下次预期采集时间和 schema 版本；不能把服务端沿用值经旧客户端转换成 `source: "history"`。旧版 API 形状可保留为只读兼容适配，新客户端使用能完整表达上述元数据的版本化契约；适配不得恢复抓取路径。
- 新增只读 `/api/intraday?date=YYYY-MM-DD`，返回固定点、适用日期的唯一临时点与覆盖情况；时间范围有上限，日期严格校验并使用参数化、带索引的查询。
- 分时图展示日由源站最后报价的 `publishedAt` 决定，而不是请求时间、返回时间或最近成功检查时间；尚无当天报价时回退最近有效日（可能早于昨天），明确标注日期。只有源站报价日期与图表所属日一致的采样可画为有效点；今日收到的旧报价不能重画为前一日的采集点。
- 若最近有效报价日已超出三日分时保留范围，卡片仍显示其报价及日期，分时区域明确提示记录已过期、可查看每日历史，不能伪造旧日内走势或触发远程补抓。
- 分时查询仅支持上述 3 个自然日，响应携带实际保留起点；过期与尚未采集区分处理，不能通过查询触发历史重抓或补造明细。
- GET 请求无论缓存是否命中都只读 D1。数据库为空时返回明确的未就绪状态（拟用 503）；不能自动抓取源站。
- 空库、数据库故障响应使用 `Cache-Control: no-store`，不得作为正常报价缓存。已有成功报价但采集失败时返回成功数据及延迟状态，不因新一轮抓取失败清空数据。
- 分钟查询初期目标共享缓存窗口为 15 秒；缓存较旧时仍可能读到上一轮，不保证恰好一分钟刷新。使用短且有界的陈旧服务窗口；不能让无界 stale-while-revalidate 掩盖持续故障，也不能将包含旧临时点的同步响应长期作为服务器分钟归档。每日历史内容可以更长缓存，版本与游标必须与返回内容一致。
- 实施时核对 Next.js 本地对应版本文档及 OpenNext 对动态查询路由的缓存行为，线上检查实际命中与过期；不能仅凭 `revalidate` 或响应头断言缓存生效。
- 浏览器先显示本地缓存，再查询服务端；刷新按钮只获取服务器已有结果，不是“立即重新抓取银行报价”。打开、唤醒仍刷新服务端视图，同步合并防重复。
- 页面持续可见且在线时，每 60 秒向服务端请求增量同步；隐藏、离线或卸载时停止轮询，恢复前台立即带本地游标续传。同一时间只运行一次请求序列，已有值与布局保留。轮询只查询服务端，不触发源站采集。
- 报价日期早于今天时显示“今天无更新”；当天报价发布时间落后服务端最近检查时间至少 5 分钟才显示“当前无更新”，不以价格是否变化判断。
- 在线数据以服务端为准，IndexedDB 作为可重建副本；旧版客户端数据保留用于离线，但不得上传为服务器权威记录或覆盖服务器历史。
- App 继续保留本地存储和离线能力：IndexedDB 保存已同步的每日历史与分时数据，Service Worker 缓存应用资源；不能只保留服务器数据而删除设备端副本。离线只能查看已下载内容，不会后台取得新报价，首次从未在线缓存的设备不保证可离线打开。
- 服务端过期删除不会主动擦除离线设备的数据。App 恢复在线后同步保留范围并清理本地过期分时明细；离线期间可保留上次缓存供查看，明确标为缓存数据，不能暗示仍在更新。每日历史不随分时明细清理；本期不新增本地每日历史自动过期策略。
- IndexedDB 迁移须带 schema 版本；正常使用增量协议，首次或失效重建才获取有限范围快照。服务器完整窗口快照按权威内容替换该窗口，不能仅 upsert 导致旧填补值或已撤回记录残留。失败或不完整响应不删除缓存，窗口之外仍保留离线副本。
- 保持现有系统主题、加载结构、画布 resize 和 Serwist `defaultCache`。核对新版 API 与旧 SW 缓存过渡；元数据缺失时不能显示为新鲜数据。
- SW 的 NetworkFirst 可能回退到旧响应，HTTP 200 或 `navigator.onLine` 均不证明数据来自网络；新鲜度根据响应内快照时间与采集状态计算。验证网络 503 的实际行为，必要时依靠 IndexedDB 保留数据，不假设 SW 遇到任意 5xx 一定自动回退。

### 4.1 App 增量同步协议

1. **首次加载或旧版本迁移**：先显示设备已有缓存，再请求 bootstrap 快照，只含默认最近一年每日历史、三日固定点、唯一临时点及新鲜度信息，不下载服务器全部长期历史。返回 `datasetId`、schema 版本、保留起点与一致的同步游标；旧格式客户端数据不能充当新协议游标。
2. **正常每分钟同步**：拟用 `/api/sync?cursor=...`，只返回该游标之后发生变化的实体的当前值：通常是一个临时点和采集状态，每 5 分钟增加一个固定点，另含历史修正和删除。即使用户漏掉数轮同步，也只需接收当前临时点与遗漏的固定点，不回放每个被覆盖的分钟价格；不重复下载整日、三日或一年历史。
3. **临时点替换与删除**：临时点使用稳定键 `live:<currency>`，每分钟是更新该键，不是不断追加新点。到固定分钟后原子新增固定点并清空临时点，App 同步相同操作；保留 `delete` / 空临时点语义，避免 10:04 留在本地。返回 `retainedFrom`，使客户端可按范围一次删除三日前固定点。长期每日历史不受此清理影响。
4. **不能按报价时间当游标**：同一报价时间可能多次被采到、历史日期可能修订或删除，使用服务端提交顺序的单调版本游标，并含数据集身份与作用域。`sync_changes` 只记录变更版本、实体键及删除，不记录每次临时点的价格 payload；将多次变动按实体键合并后，从一致的业务快照读取当前值。被覆盖的分钟价格不会因同步日志而继续保存。
5. **一致性和失败恢复**：一次响应的当前实体值、删除项、保留边界和返回游标必须来自同一数据库读快照。不能先取高水位、再读并发更新后的当前实体却仍返回旧游标；也不能在新游标下漏掉已提交变化。App 在同一个 IndexedDB 事务中提交改动与游标；失败保留原游标，重试幂等，拒绝旧缓存造成的游标回退或不同数据集补丁。初版默认范围有界，增量响应合并实体后一次返回；若超过安全大小，明确要求重建受影响有限窗口，不截断变更却推进游标。
6. **游标过期**：变更日志保留 3 天。超过可续传范围、测试库被重建或 schema 不兼容时，服务端明确返回 `resetRequired`，客户端重新获取上述有限窗口，并重建游标；不要求下载全部长期历史。中途先保留可用离线缓存，成功后再替换受影响窗口。
7. **额外范围按需获取**：初版 bootstrap 已含三日分时，额外更早的每日历史按需获取；游标必须标注实际覆盖范围，不能把未下载数据当已同步。超过日志保留范围后，旧本地历史未必仍是最新，重新查看该范围时须做按范围校验或替换，不能用最近一年窗口的重建冒充全库已同步。
8. **离线和重新上线**：离线读取 IndexedDB，不请求或清空数据；恢复网络后先尝试增量。服务器按需提示局部重建；清理在成功同步后进行，不能依设备时钟提前删除唯一离线副本。

实施前细化 payload、版本作用域、读快照一致性和最大响应大小。增量同步 API 可使用小幅共享缓存，但完整游标必须参与缓存键；不能将一个客户端的游标响应复用给另一个游标。重建只涉及服务端已有数据，永不触发源站抓取。

### 4.2 API 升级与本地重建

- API 协议版本、D1 结构版本、报价修订号、数据集 ID 分开管理；普通报价更新不触发页面刷新。
- 客户端声明 API schema；不兼容时服务端明确返回 426 与目标 schema，普通 503、断网和解析错误不能当作升级。
- 包含此机制的客户端在线且可见时自动整页刷新，同一目标协议版本只尝试一次并持久保存防循环标记。已经运行且未包含此逻辑的旧 App 仍需先在线刷新一次。
- 刷新后新版与 API 兼容，先获取并验证有限窗口快照，再在单个 IndexedDB 事务中清空旧业务副本和游标、写入新数据；失败不清旧数据。
- 只清理过期 API 响应缓存，不删除 SW 或新版程序资源，也不删除服务端 D1。重建后只能恢复服务端仍保留的数据，不能补造已过期分时。
- 数据库显式重建后更换数据集 ID；相同 API 下客户端获取新快照并重建本地副本，不反复整页刷新。

### 4.3 后端结构升级时机

- 结构兼容性移至显式部署前检查，含结构代次和必需字段；API / Cron 不逐次查询或比较结构代次。实际 SQL / 数据错误停止操作并按未就绪处理，禁止运行时自动删库或重建。
- 迁移放到部署流程：构建与本地验证 → 备份 → D1 migration → 兼容性及数据就绪检查 → 发布 Worker → 运行验证。
- 兼容新增字段仍保持同一结构代次，migration 编号不等于不兼容版本。无法迁移的生产改动建议新库重建、导入可保留历史、验证后切换绑定并轮换数据集 ID，不自动清掉长期历史。
- 破坏性重建前先暂停旧采集；新库数据就绪且查询验证通过之前不切换流量，切换后保留旧库作为回退依据。
- 全量重建需要明确操作和可恢复备份；日内报价无法靠现价接口完整回填。统一发布入口先应用远程迁移、显式校验并初始化数据，之后发布两个 Worker；通用 build / 本地 preview 不操作生产。未授权部署期间只在本地验证。

## 5. 免费计划预算与验证

- Cron 使用 Workers 额度；免费每次 CPU 10ms 是关键限制，等待网络与数据库 I/O 不计 CPU。独立 Worker 可以减少框架开销，但不保证整份 HTML 的 cheerio 解析能稳定达标。
- D1 免费额度为每日读 500 万行、写 10 万行，账号总存储 5GB、单库 500MB。实际读取、索引维护、运行状态、清理与历史同步都计入预算，两个环境共享账号额度。
- 快照写入量预计远低于免费日额度；不能据此保证全站免费，仍须实测网站 Worker、采集 Worker 的 CPU、D1 查询计划、存储增速与 R2 使用量。历史校准按实际部署 / 显式回填次数计量，另计初始化与清理。
- 客户端每分钟轮询需要单独预算：一台设备全天前台约 1,440 轮/天，一轮通常一次增量 API 请求，bootstrap 或额外历史另计。不能只用 1,440 次采集估算全站用量。每日历史 API 单次最多 366 个日期、分时快照单日最多 288 个固定点外加适用日期的唯一临时点；使用日期和变更版本索引，避免每次扫描全部任务或变更历史。依据 D1 返回的实际读写行数计量。
- 分钟采集后的状态覆盖、固定点维护、同步变更标记和过期删除都消耗 D1 写额度；只保留一个临时点可减少存储，但不消除每分钟写入成本。测试中单独记录每轮总写入，再外推全天和双环境预算。
- 测试环境启用结构化运行日志与合适采样的观测，记录任务延迟、成功 / 失败、解析和数据库耗时、CPU、D1 读写量；先取得基线，再评估是否增加外部告警服务。
- 若 CPU 持续超限，先定位解析或框架瓶颈；不以丢弃错误或降低数据校验绕过限制。必要时单独评估 Workers Paid（最低 5 美元/月），不自动升级账户。

## 8. 本轮审阅结论

已修订的主要缺口：

1. 历史校准游标混用当日采样会漏掉前日数据，改为独立确认游标与待修复范围。
2. 计划时间、请求时间和返回时间混淆会污染分钟归属，现以实际发起时间截断到分钟；固定点回退保留真实来源，不能连续沿用。
3. 前台缺少自动查询、客户端只 upsert 不能反映服务端撤回或纠正，补充轮询和权威窗口替换。
4. 缺测统计会忽略未执行 Cron，补充策略生效时间、采集起点和预期槽位推导。
5. 分支与云端资源并不自动隔离，Vercel 预览部署也可能继续触发，提前到首次推送前检查。
6. 两周观察不应无条件阻塞初版上线；普通旧版回滚又会恢复用户触发抓取，分别修正验收与回退边界。

7. “最近五分钟的全部分钟点”与用户意图不符，已改为固定 5 分钟点加唯一临时点，固定分钟优先用该分钟请求结果。
8. 同步日志若保存完整临时点 payload 会暗中保留全部分钟历史，改为仅记录变更实体标记并返回其当前值；同时明确读快照和游标必须一致。

图表与时间归属已确认，没有继续阻塞规划的产品语义问题。其他初始参数可根据测试数据调整；正式资源、价格与部署状态以实施时核验为准。
